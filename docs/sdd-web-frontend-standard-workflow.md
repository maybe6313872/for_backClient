# sdd-web-frontend 标准流程全链路

## 1. 文档目的

本文总结 `sdd-web-frontend` skill 的标准工作方式，面向浏览器端 Web 单页应用的前端开发、迭代和存量项目接手。

本文只说明流程、职责、门禁、文档产物和证据规则，不描述任何具体业务需求、页面或项目实现。

skill 的核心目标不是“尽快修改代码”，而是让每次修改都具备：

- 可追溯的需求来源。
- 明确的设计和实现边界。
- 用户逐阶段确认的过程控制。
- 与代码相匹配的测试证据。
- 可回滚、可交接、可继续迭代的项目文档。

## 2. 适用范围

该 skill 面向以下技术形态：

- 浏览器端 Web SPA。
- React 或 Vue。
- TypeScript。
- Vite。
- SCSS 或项目既有 CSS 体系。

典型项目识别依据：

- `package.json`
- `vite.config.ts/js/mjs`
- `react` 或 `vue` 依赖
- `tsconfig.json`

不属于本 skill 的典型项目包括 Svelte、Next.js、Nuxt、Astro、SolidJS、Electron、Webpack 主导项目以及 SSR/SSG 项目。

## 3. 两种工作模式

### 3.1 Mode A：正向规格驱动开发

适用于：

- 新功能开发。
- 存量功能迭代。
- 页面、组件、状态、接口或交互调整。

标准链路为：

```text
项目认知
    |
    v
constitution -> spec -> design -> tasks -> test -> deliver
       ^             每阶段完成后暂停并等待用户确认
       |
       +------ 发现冲突或风险时回流到 spec/design
```

Mode A 的主要产物是：

- 六阶段 `specs/` 工作台。
- 实际源代码。
- 测试与运行证据。
- `README`、`context/`、`task.md` 等项目认知文档的同步更新。

### 3.2 Mode B：代码文档孪生

适用于：

- 接手老项目。
- 逆向梳理现有代码。
- 建立项目代码地图、模块索引和知识地图。

Mode B 的目标不是改功能，而是建立与源码事实等价的认知层：

- 项目 README。
- 功能、架构、数据、状态、模块和场景文档。
- 代码地图。
- 知识地图。
- 证据追溯和未决问题。

如果项目没有可靠的 `specs/` 认知基础，但已有大量存量代码，通常应先执行 Mode B，再执行 Mode A。

## 4. 每次触发后的入口链路

无论用户使用斜杠命令还是自然语言表达，skill 进入项目后都应按以下顺序处理。

### 4.1 读取用户偏好

读取用户偏好文件，应用表达方式、语气和协作习惯。

偏好只能影响表达，不得改变以下硬规则：

- 必须分阶段。
- 必须经过 Gate。
- 必须先计划再写代码。
- 必须 archive-first。
- 必须保留证据边界。
- 不能用“通过”掩盖未验证事实。

### 4.2 读取项目认知

首先读取：

1. `specs/README.md`
2. `specs/task.md`

然后按任务需要读取：

- `specs/context/*`
- `specs/open-issues.md`
- `specs/retro/`
- `docs/`
- 相关源码和配置。

如果 `README`、`specs/` 和存量代码都不存在：

- 新项目可以从 Mode A 的 constitution 开始。
- 老项目应先建立 Mode B 项目认知。

### 4.3 检查需求收件箱

检查 `docs/requirements/` 是否有待签收资料。

如果存在输入，必须按以下顺序处理：

1. 登记到 `task.md`。
2. 复制到规格目录中的输入归档位置。
3. 登记来源和副本关系。
4. 清理已签收的收件箱文件。

清空收件箱只代表“已接收”，不代表需求已经完成。

### 4.4 确认 skill 路由

先判断当前项目是否属于浏览器端 Web SPA，再判断用户意图：

- 实现、修改、修复、优化功能：进入 Mode A。
- 梳理、接手、建立代码地图：进入 Mode B。
- 规整工作台：执行文档维护流程。
- 整理 `docs/`：执行文档治理流程。
- 复盘：执行 retro 流程。

项目不属于本 skill 时，应移交给对应领域 skill，而不是强行套用 Web 前端流程。

### 4.5 入口归档检查

开始新迭代前，检查：

- `task.md`。
- 所有阶段 `current.md`。
- 外部输入副本和 `sources.md`。
- 上轮 retro 台账。

上一轮任务或工作台不能直接覆盖。必须先归档，再创建本轮工作台。

### 4.6 处理 `docs/` 中的二进制资料

如果 `docs/` 中有 xlsx、pdf、docx 等资料，先按文档适配器规则完成文本化，再将转换结果和原始来源登记到认知文档。

没有事实来源的内容不能凭经验补写。

## 5. 六阶段总览

| 阶段 | 核心问题 | 主要产物 | 是否允许写业务代码 |
| --- | --- | --- | --- |
| constitution | 项目必须遵守什么工程约束？ | `1-constitution/current.md` | 否 |
| spec | 要实现什么，什么算完成？ | `2-spec/current.md` | 否 |
| design | 准备用什么结构实现？ | `3-design/current.md` | 否 |
| tasks | 如何拆分并实际完成实现？ | `4-tasks/current.md` 与源码 | 是，需用户批准计划后 |
| test | 证据是否足以支持结论？ | `5-test/current.md` | 否，主要执行和记录验证 |
| deliver | 如何交付、回滚和同步文档？ | `6-deliver/current.md` 与交付文档 | 否 |

每一阶段都必须经历：

```text
准备 -> 产出本阶段内容 -> 自检 -> 更新 task.md -> Gate -> 停止等待用户确认
```

不得自动连续跑完六个阶段。

## 6. Gate 的共同机制

### 6.1 Gate 的目的

Gate 是阶段边界，不是形式化打勾。它用于确认：

- 本阶段内容是否完整。
- 是否混入了其他阶段内容。
- 事实是否有来源。
- 下一阶段是否具备开始条件。
- 用户是否同意继续推进。

### 6.2 每个 Gate 的固定动作

每阶段结束时必须：

1. 运行本阶段自检。
2. 汇报已完成、未完成、阻塞项和下一步。
3. 同步 `task.md`。
4. 输出阶段产出摘要。
5. 逐条输出 Gate 检查结果。
6. 明确告诉用户需要确认什么。
7. 停止，等待用户明确回复“通过”或指出修正意见。

用户确认通过后，才进入下一阶段。

### 6.3 通用 Gate 编号

六阶段共同使用以下通用 Gate：

| 编号 | 含义 | 作用 |
| --- | --- | --- |
| G1 | 阶段职责边界 | 防止把需求、设计、任务、测试和交付内容混写。 |
| G2 | 归档纪律 | 防止覆盖或删除历史规格，保证 archive-first。 |
| G3 | 证据分级 | 防止把低等级验证包装成高等级结论。 |
| G4 | 进度透明 | 每次 Gate 前说明已完成、未完成、阻塞和下一步。 |
| G5 | specs-first 配对 | 每个业务代码改动都必须有对应规格登记。 |
| G6 | claim-git 配对 | 交付前核对声明的文件、证据和实际工作树一致。 |

领域专用 Gate 使用领域前缀，例如 Web 前端使用 `FE-*`，不能占用 `G` 编号。

## 7. Constitution 阶段

### 7.1 作用

constitution 定义项目级的“不可随意改变的规则”。它解决的是“以后所有实现都必须遵守什么”，不是“本次具体要做什么”。

### 7.2 应记录的内容

- 技术栈和框架版本。
- Node、包管理器和构建工具。
- 目标浏览器范围。
- CSS、组件和代码风格基线。
- 最小改动原则。
- 决策优先级。
- 不可触碰的业务、接口和目录边界。
- 路由、移动端、可观测性、i18n 等条件能力是否适用。
- 测试和证据边界。

包管理器必须根据实际 lockfile 和 `package.json` 判断：

- `package-lock.json` 对应 npm。
- `pnpm-lock.yaml` 对应 pnpm。
- `yarn.lock` 对应 yarn。
- `bun.lockb` 对应 bun。

不能因为组织默认偏好而强行更换现有项目的包管理器。

### 7.3 禁止内容

constitution 不应包含：

- 本次具体功能需求。
- 具体组件 Props。
- 详细任务列表。
- 测试用例。
- 函数实现方案。

### 7.4 Gate 重点

- 工程约束是否足够少且足够明确。
- 技术栈、包管理器和浏览器基线是否来自事实。
- 条件能力是否逐项判断为“设计”或“N/A + 原因 + 确认人 + 残余风险”。
- `task.md` 是否标记 constitution 阶段完成。

## 8. Spec 阶段

### 8.1 作用

spec 定义“要实现什么”和“什么情况下算满足”。它把用户的自然语言目标变成可观察、可验收的需求。

### 8.2 应记录的内容

- 需求目标和使用场景。
- 每条需求的验收标准。
- 正常流程和异常流程。
- 空数据、错误、超时、权限、非法输入和大数据量边界。
- 多语言、响应式、浏览器和无障碍范围。
- 每条需求对应的证据定义。
- 关键澄清问题及其答案。
- 非目标和明确不做的内容。

每条需求都要能够回答：

- 谁在什么前置条件下执行什么动作？
- 页面或系统应该出现什么可观察结果？
- 哪些情况不属于本轮范围？
- 如何证明该结果成立？

### 8.3 澄清规则

需求不清时先提问，不能直接进入设计。澄清问题应优先覆盖：

- 功能范围。
- 文案和语言范围。
- 浏览器和响应式范围。
- API 或外部输入事实。
- 状态和异常边界。

最多分批提出有限数量的问题；关键歧义未关闭前不得进入设计。

### 8.4 禁止内容

spec 不应包含：

- Zustand、Redux 等具体实现选型。
- 组件文件拆分。
- Props 和事件接口。
- 任务编号和代码修改清单。
- 具体测试函数或测试代码。

这些内容分别属于 design、tasks 和 test。

### 8.5 Gate 重点

- 每条需求都有验收标准。
- 主要异常和边界已覆盖。
- 每条需求都有证据定义。
- 关键澄清已关闭。
- `task.md` 已更新。

## 9. Design 阶段

### 9.1 作用

design 解决“如何实现”。它把需求映射成组件结构、数据流、状态边界和技术方案。

### 9.2 应记录的内容

- 组件树和职责。
- Props、Events、Slots 或回调接口。
- 状态分类与所有权。
- 表单、表格和复杂度拆分方案。
- API 和外部数据边界。
- 异步状态矩阵。
- 缓存 owner、key、失效映射和恢复规则（适用时）。
- 响应式和可访问性方案。
- i18n 资源归属、fallback 和语言切换影响。
- 路由、可观测性和移动端适用性判断。
- 方案与需求验收点的追溯关系。

### 9.3 六类状态必须明确归属

| 状态类别 | 需要回答的问题 |
| --- | --- |
| Server | 后端返回的数据由谁拥有，何时刷新？ |
| UI | 展开、选中、hover、弹窗等纯界面状态由谁拥有？ |
| Form | 输入值、校验、提交状态由谁拥有？ |
| Flow | 页面步骤、流程门禁和跳转由谁拥有？ |
| Persistence | localStorage、sessionStorage、离线数据由谁拥有？ |
| Shared | 跨模块共享状态由谁拥有，如何保持一致？ |

### 9.4 异步设计要求

每条请求或命令路径都要考虑：

- idle。
- loading。
- 成功且有数据。
- 成功但无数据。
- error。
- 旧数据刷新失败。
- cancelled。
- command 的去重行为。

如果有缓存、轮询、离线恢复或写入后刷新，还要写清：

- cache owner。
- cache key。
- freshness。
- write path 到 invalidation key 的映射。
- 聚焦、轮询、恢复和并发写入行为。

### 9.5 复杂度判断

遇到表格、复杂表单、跨模块状态或多交互组件时，需要根据责任耦合和交互复杂度判断：

- 是否抽取共享组件。
- 是否使用已有库。
- 是否保持原生实现。
- 选择的收益和代价是什么。

不能只按代码行数机械拆分，也不能无理由引入重量级依赖。

### 9.6 Gate 重点

- 组件接口是否完整。
- 状态分类和工具选型是否合理。
- 异步矩阵和缓存模型是否完整。
- API 契约边界是否有事实来源。
- 条件能力是否逐项完成设计或记录 N/A。
- 设计是否都能追溯到 spec。

## 10. Tasks 阶段

Tasks 是“拆任务并实际实施”的阶段，不是只写计划的阶段。它分为两个必须分开的子阶段。

### 10.1 Phase 1：实施计划

先把设计拆成可执行任务。每项任务至少写清：

- 任务编号。
- 对应的需求和验收点。
- 要遵守的 `RULE-*` 规则。
- 要修改的文件或模块。
- 实施目标。
- 预期验证和证据。
- 风险和依赖。

这一阶段只写计划，不写源码。计划完成后执行 Gate ①，等待用户批准。

### 10.2 Phase 2：实际执行

Gate ① 通过后，按计划逐项写真实代码，并完成该任务应有的测试。缺陷修复通常应先写能复现问题的测试，再修复代码。

执行过程中必须：

- 按任务顺序更新进度。
- 保持源码和 specs 配对。
- 发现需求变化时回流到 spec。
- 发现技术方案变化时回流到 design。
- 不把尚未实施的任务写成完成。
- 保留可复现的命令和结果。

完成 Phase 2 后执行 Gate ②，等待用户确认，再进入 Test 阶段。

### 10.3 `task.md` 与 `4-tasks/current.md` 的区别

| 文件 | 作用 |
| --- | --- |
| `specs/task.md` | 全局任务看板，记录粗粒度目标、阶段状态、阻塞和下一步。 |
| `specs/4-tasks/current.md` | 当前六阶段迭代的细粒度施工计划、执行记录和证据。 |

不能把详细 T1/T2/T3 任务塞进全局 `task.md`，也不能只更新 `4-tasks` 而不更新全局看板。

### 10.4 Gate 重点

- 每项任务都映射到需求验收点。
- 每项任务都有文件范围和规则标签。
- Gate ① 已获用户批准。
- Phase 2 已写入真实代码和必要测试。
- 代码、计划和 specs 保持配对。
- Gate ② 前输出完整进度表。

## 11. Test 阶段

### 11.1 作用

test 解决“证据是否足以支持结论”。它不是补写 tasks 阶段欠缺的测试设计，也不是把构建成功直接等同于功能完成。

### 11.2 应记录的内容

- 测试范围和不覆盖范围。
- 测试命令。
- 实际退出码。
- 发现的测试数量。
- 构建、类型检查和 lint 状态。
- 单元测试、集成测试和 E2E 状态。
- i18n 一致性检查。
- API 异常和非 JSON 响应边界（适用时）。
- 异步状态矩阵的验证情况。
- 浏览器、axe、Lighthouse、性能检查情况。
- 每条结论的证据等级。
- 未配置、未执行、失败和残余风险。

### 11.3 测试状态必须由事实派生

允许的状态包括：

- `passed`
- `failed`
- `ran-but-zero-tests`
- `configured-not-run`
- `missing`
- `N/A`

其中：

- 命令未执行不能写成 passed。
- 测试运行但发现 0 项不能写成 passed。
- 命令失败不能写成 passed。
- 工具缺失应写明原因和残余风险。
- N/A 必须有适用性理由、确认人和残余风险。

### 11.4 证据等级

skill 使用固定的 L1-L5 证据体系。具体等级定义以 skill 的 `evidence-gate-protocol.md` 为唯一事实源；其他文档不得自行重新定义等级含义。

使用原则：

- 每条测试结论都标注证据等级。
- 证据等级由真实可复现资产支撑。
- 交付结论不得高于测试阶段达到的最高证据等级。
- 未验证的浏览器、真实设备、网络和性能边界必须写入残余风险。

### 11.5 用户人工验证的定位

用户人工验证可以作为 UI 现场证据，但必须明确：

- 检查了什么页面和状态。
- 使用了什么环境。
- 用户确认了什么结果。
- 没有检查什么。

人工验证不能替代未配置的 E2E、axe、Lighthouse 或真实生产验证，也不能替代代码和构建证据。

### 11.6 Gate 重点

- build、typecheck、lint、unit、E2E 分别派生状态。
- i18n 检查结果真实可追溯。
- 需求验收点有对应验证。
- 未执行项和风险没有被隐藏。
- 每条结论有证据等级。
- 用户人工验证已明确记录或仍保持未完成状态。

## 12. Deliver 阶段

### 12.1 作用

deliver 负责把实现变成可交接、可回滚、可继续维护的交付候选包。它不新增需求，也不在此阶段改变设计。

### 12.2 应记录的内容

- 变更摘要。
- 实际交付文件。
- 需求、设计、任务和测试的对应关系。
- 测试与用户验证证据。
- 变更日志和 release note。
- 回滚策略。
- 已知限制和残余风险。
- 是否提交、部署或推送。
- 交付语义与最高测试证据等级的关系。
- README、context、代码地图和知识地图同步情况。

### 12.3 回滚要求

回滚策略必须可执行，不能只写“必要时回滚”。至少应说明：

- 回滚基线或版本标识。
- 要恢复的文件或构建产物。
- 新增文件如何处理。
- 是否涉及数据库、API、部署或数据迁移。
- 用户已有的无关改动如何保护。

### 12.4 G6 工作树核对

交付前核对：

- `git status` 中是否有声明之外的改动。
- 声明修改的文件是否真实存在。
- 声明的测试证据是否真实存在。
- 是否有未登记的新增文件。
- `docs/requirements/` 是否按要求完成签收和清理。
- 用户已有的脏工作树变更是否被误删或误算进本轮。

### 12.5 文档同步

交付前同步适用的文档：

- `specs/README.md`
- `specs/context/features.md`
- `specs/context/modules.md`
- `specs/context/knowledge-map.md`
- `specs/context/evidence-trace.md`
- `specs/context/iteration-log.md`
- `specs/open-issues.md`
- `specs/retro/`
- `CHANGELOG` 或 release note

### 12.6 Gate 重点

- 交付记录完整。
- release note 和变更日志已更新。
- 回滚可执行。
- 文档与源码同步。
- `task.md` 已写完成状态、五行摘要并归档。
- G5 和 G6 均通过。
- retro 判断已完成。

## 13. Archive-first 生命周期

### 13.1 基本规则

`specs/` 下的工作台不能直接覆盖或删除。任何更新前先归档旧内容，再写新内容。

对应关系：

| 当前文件 | 历史目录 |
| --- | --- |
| `specs/task.md` | `specs/task/` |
| `specs/1-constitution/current.md` | `specs/1-constitution/history/` |
| `specs/2-spec/current.md` | `specs/2-spec/history/` |
| `specs/3-design/current.md` | `specs/3-design/history/` |
| `specs/4-tasks/current.md` | `specs/4-tasks/history/` |
| `specs/5-test/current.md` | `specs/5-test/history/` |
| `specs/6-deliver/current.md` | `specs/6-deliver/history/` |

### 13.2 归档要求

- 保留旧文件的完整原文。
- 使用日期和说明命名归档文件。
- 更新对应 `INDEX.md`。
- 新工作台重新写入三字段 header：迭代标识、日期、状态。
- 不用滚动的单一 `archive.md` 代替按任务归档。
- 不把 `context/iteration-log.md` 当作完整归档的替代品。

### 13.3 什么时候触发归档

- 开始新迭代。
- 切换任务。
- 当前阶段进入下一轮。
- 交付完成并准备接收新任务。
- 需要修正已经写入的工作台内容。

## 14. 代码质量规则族

除阶段门禁外，skill 还通过规则族约束实现质量：

| 规则 | 关注点 |
| --- | --- |
| `RULE-STATE` | 状态分类、所有权和状态库选型。 |
| `RULE-RENDER` | key、列表稳定性、受控输入、派生状态和 effect。 |
| `RULE-ASYNC` | 请求矩阵、竞态、取消、缓存、去重和恢复。 |
| `RULE-TYPE` | 类型严格性、外部契约风险和运行时校验。 |
| `RULE-A11Y` | 语义 HTML、键盘、焦点、ARIA 和 WCAG。 |
| `RULE-PERF` | LCP、INP、CLS、包体积和性能边界。 |
| `RULE-SEC` | XSS、令牌、CORS/CSRF、依赖和敏感数据。 |
| `RULE-STYLE` | 样式隔离、命名、主题和全局泄漏。 |
| `RULE-I18N` | 语言资源、fallback、动态文案和切换回归。 |
| `RULE-CMPX` | 复杂组件、表格和表单的拆分与工具选型。 |
| `RULE-PROC` | 计划先行、未经授权不编码、证据和归档纪律。 |

规则的详细约束和反例以 skill 的 `coding-rules.md` 为准。

## 15. 需求或实现冲突时的回流

任何阶段发现以下情况，都不能静默继续：

- 需求与现有实现冲突。
- 外部接口事实不清。
- 设计无法满足验收点。
- 任务文件范围不足。
- 测试发现需求定义不完整。
- 交付证据不足以支持原计划结论。

处理方式：

1. 停止当前阶段。
2. 说明冲突事实和影响。
3. 指定需要回流的阶段。
4. 更新 `task.md`。
5. 等待用户确认。
6. 修改对应规格或设计。
7. 重新执行受影响的 Gate。
8. 回到原流程继续推进。

不能用代码注释、临时判断或文档措辞掩盖未解决的契约缺口。

## 16. 一次完整迭代的用户协作节奏

用户通常会经历以下确认点：

1. 确认 constitution：认可工程约束和范围边界。
2. 确认 spec：认可需求、验收标准和非目标。
3. 确认 design：认可组件、状态、接口和技术方案。
4. 确认 Tasks Phase 1：认可任务拆分和源码文件范围。
5. 确认 Tasks Phase 2：认可代码已按计划完成，进入测试。
6. 确认 Test：认可自动化结果、人工结果和残余风险。
7. 确认 Deliver：认可最终交付记录和交付边界。

每次“通过”只代表通过当前阶段 Gate，不代表自动跳过后续阶段。

## 17. 小改动如何使用这套流程

小改动也必须先判断它属于哪类工作：

- 如果是六阶段迭代中的需求或 UI 变更，仍按 Mode A 走完整链路，但每阶段内容可以保持精简。
- 如果是单点、低风险、明确的 bug 修复，可按 skill 规定的精简修复流程执行，但至少要更新 `task.md`、保留规格登记、验证结果和证据边界。
- 如果是目录整理或文档归档，应使用专用命令，不要伪装成业务开发任务。

“改动很小”不能成为跳过计划、归档、验证或交付留痕的理由。

## 18. 最终自检清单

交付前应逐项确认：

- [ ] 项目路由和工作模式判断正确。
- [ ] `README.md`、`task.md` 和必要 context 已读取。
- [ ] 旧工作台已 archive-first 归档。
- [ ] 每个阶段只写了本阶段应有内容。
- [ ] 每个 Gate 都停下来等待了用户确认。
- [ ] 需求、设计、任务、代码和测试可以互相追溯。
- [ ] 每项代码改动都有 specs-first 配对。
- [ ] 真实包管理器、浏览器基线和工具链未被臆测。
- [ ] 异步、状态、缓存、i18n、可访问性和复杂度边界已判断。
- [ ] 测试状态来自实际命令和可复现证据。
- [ ] 未执行项、缺失工具和残余风险已如实记录。
- [ ] 交付声明没有超过测试证据等级。
- [ ] `git status` 与交付声明一致。
- [ ] 回滚基线和步骤可执行。
- [ ] `task.md`、历史索引、context、CHANGELOG 和 release note 已同步。

## 19. 一句话总结

`sdd-web-frontend` 的标准流程是：先建立事实和约束，再定义需求、设计方案、拆解并实施代码，随后用可复现证据验证，最后完成可回滚交付和文档同步；每个阶段都必须经过用户确认，任何不确定事实都必须停下来澄清，而不是凭经验继续。
